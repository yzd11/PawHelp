# 评测集说明

## 检索评测集

`customer_service_500.csv` 以本项目 `knowledge/` 下的 16 份知识文档为准，共 500 题：

| 桶 | 题数 | 说明 |
|---|---:|---|
| `A_policy` 政策 | 100 | 退换货、运费、积分优惠券、发票、物流异常、账号安全 |
| `B_model` 型号 | 80 | 型号参数、对比、耗材型号 |
| `C_colloquial` 口语 | 100 | 不用文档术语的口语问法 |
| `E_multi` 多要点 | 100 | 需要组合多个事实或证据组，不保证每题都跨不同文件 |
| `F_identifier` 标识符 | 30 | 故障代码、滤芯/耗材编号等精确字符串 |
| `D_absent` 库外 | 90 | 文档没有依据，应原样拒答 |

**这是自建评测集。** 知识文档和题目全部由 AI 生成，不含真实客户数据或第三方数据集，
未经业务方核准。最早的 300 题与 4 份文档来自项目初版，之后新增 12 份文档和 200 题。为减少“照着文档出题”的偏差，新题先于新文档写成，
库外题避开新文档的话题。用字符二元组衡量题干与标准章节的字面重合度：
旧题平均 0.40，新题 0.33（新口语题 0.11），新题并不比旧题更容易字面命中。
分数只用来比较本项目内的检索策略，不代表真实客服流量上的效果。

本基准只检索 `app/evaluation/corpus.py` 中 `EVALUATION_SOURCES` 所列文档同步产生的知识块。
产品库里保留的人工和历史条目不计入基准，也不会成为本基准的检索结果。
运行前会逐块对照当前 Markdown 与已向量化的 MySQL 记录；有旧版、缺失或
待向量化块就拒绝运行，避免付费生成无效报告。

可回答题的 `期望章节` 指向当前知识文档的章节；`标准要点` 是该题必须回答的
事实和条件，须能从所标章节找到。库外题不填标准要点和期望章节。
已对流程、适用条件、否定规则、型号对比逐题补齐或收窄题干；对文档没有说明的
会员运费抵扣优先级，只分别评已明示的一般规则和会员权益，不猜唯一结算结果。
修改文档或题目后先运行：

```powershell
python -m pytest -q tests/test_eval_knowledge_alignment.py tests/test_evaluation_corpus.py tests/test_retrieval_quality_eval.py
```

这项检查验证**每个必需章节至少有一个含标准要点的知识块**，以及每个要点
都可在所标章节证据中找到；它不能证明业务规则在现实中正确，或生成答案的
语义一定正确。数字归属、否定方向、起算点仍需要人工审核。
页面的“自动匹配知识块”不是 CSV 中预填的固定数量：只在评测语料范围内按
知识块的末级标题匹配 `期望章节`，且知识块答案必须含该题至少一个标准要点，
才把它列入 GT。父级章节下的无关块不会仅因路径含别名就得分。`+` 表示
每个章节组都必需，`|` 表示一组内的可替代标题；块 ID 会随重建改变。
这仍是**文档和要点派生的 GT**，不是独立人工逐块标注的检索相关性判断。
没有现行知识文档依据的会员门槛、礼品、积分兑换、纸质发票等规则，不能为了
提高评测分数而补写；需要先由业务方确认并正式维护知识文档。

修改本 CSV 后，既有 `reports/retrieval-evaluation.json` 仍是旧题目产生的历史报告，
不得与新题目混读。须重新运行评估才能得到新的检索与生成分数；完整运行会产生
模型调用，不能仅修改历史报告里的数字。
若修改了 `knowledge/` 文档，还须先在知识库工作台同步 Markdown、补齐向量，
确认数据库中的知识块已更新，再重新评估；只改本地文件不会自动更新检索索引。

## 结果解读

BM25 在口语问法上排序最弱，在故障码、耗材编号上排序最好；混合检索补足召回，重排主要提升排序。证据门控偏保守：库外题全部原样拒答，代价是 17 道可回答题被误拒。证据门控的相关性阈值按线上路径（模型改写 + 复合问题拆分 + 全库检索）采集的 96 题重新校准，从 0.127 升到 0.174，独立验证 24 题无误收、有用召回 0.95。误拒中 13 道是口语、极短问法或故障码对比，正确知识块都已召回、多排在首位（F28 只召回一半），但重排分低于阈值，其中 4 道分数在 0.127 到 0.174 之间，是阈值上调的代价；4 道通过粗筛后 Jev 落在中间带、交给大模型核验，被判为不足，要点都在证据里，核验要求的更多（“为什么分包裹”的原因、未点名的消毒液、“会不会烧起来”的保证、E5 场景下的配网步骤），偏严；没有完全未召回的题。阈值附近可回答题与库外题的分数交叠，放宽粗筛只会把更多库外题交给大模型核验。上表为 2026-10-21 以 `EVIDENCE_JUDGE=jev` 的完整运行，500 题全部评上，已包含此前对“另计”“以平台规则为准”这类答案放宽的证据核验。与 2026-10-20 只用大模型核验的运行相比：误拒 18 → 17，库外 90/90 拒答不变，Faithfulness 0.995、答案要点覆盖 0.945 不变；两次运行之间粗筛结果有几题互换（C18、C74、C92 本次通过、A32 本次未过），来自查询改写的波动。

扩充语料后评测暴露了一个检索缺陷：查询理解让大模型猜测文档分类和内容类型，并把猜测当作 Milvus 硬过滤，猜成 FAQ 时会把手册和政策整类排除。去掉推断过滤后，同一套题的纯检索对比中 hybrid + rerank 的 Recall@5 从 0.938 升到 0.996，新题从 0.894 升到 0.994；查询改写由大模型生成，每次运行的分数有小幅波动，上表为最近一次完整运行。

## Jev 证据判定评测

`scripts/run_jev_evidence_evals.py` 把最近一次 500 题报告里 hybrid + rerank 每题的证据（就是线上门控读到的那份，已截断）
交给 TypeSafe Jev，问一个是/否概率问题；大模型基线直接用报告里已记录的核验结论，不再调用大模型。标签是“可回答 / 库外”。
题号末位为 0 或 5 的题是独立验证集，在看到任何 Jev 分数前固定；阈值只用其余题选：放行线高于训练集所有库外题的概率，
拒答线低于训练集所有可回答题的概率，中间交给大模型。上线门槛：线上路径的验证题上误放、误拒都不多于大模型，且 Jev
直接决定至少一半。通过后才写 `config/jev-evidence-calibration.json`，它绑定模型版本和指令文本，任一变化即退回大模型。

```powershell
uv run python -m scripts.run_jev_evidence_evals --limit 3      # 冒烟，只打印逐题概率
uv run python -m scripts.run_jev_evidence_evals --publish      # 全量 499 题，约 60 万输入 token（约 $0.03）
```

需要 `.env` 里的 `TYPESAFE_API_KEY`，不需要数据库。2026-10-21 的结果见 [`reports/jev-evidence/jev-evidence-20261021.md`](../reports/jev-evidence/jev-evidence-20261021.md)：
线上验证 77 题误拒、误放均与大模型相同（0），Jev 直接决定 93.5%；验证集恰好没有进入核验的库外题，全部 18 道验证库外题的
最高概率 0.42，低于放行线 0.60。放行线由一道被粗筛拦下的库外题（D9，P=0.60）决定，余量不大；Jev 以英文训练为主，
换模型版本或改指令都要重跑。

上线路径的完整运行（2026-10-21，`EVIDENCE_JUDGE=jev`）：粗筛通过 403 题，Jev 直接决定 372 题（92.3%）——放行 367 题全是可回答题，
拒答 5 题（D3、D21、D29、D87、D90，P ≤ 0.03）全是库外题；其余 31 题交给大模型，这次的 4 道偏严误拒都在其中。

## 意图评测集

`intent_cases.jsonl` 检查意图识别这一步：大模型给出的 `intent`、`task_kind`、
`requested_lookups`，以及按这些字段路由后客户实际走到哪里（`route`，是否弹出订单卡片
`select_order`）。工作流只依赖这些结构化字段，不再用关键词在原话上二次猜测，所以换模型或
改 `INTENT_PROMPT` 后要先跑这一组。

- `fresh_lookup`：明确要求本轮重新查订单和物流，须按用户说的顺序填两个工具，含换说法的口语问法。
- `fresh_lookup_negative`：单项查询或政策问题，不能误填 `requested_lookups`。
- `task_kind`：通用规则问题直接检索，针对某笔订单或进度的问题绑定订单。

`intents` 可列多个可接受意图；`task_kind` 为 `null` 表示不限定，此时离线测试会验证
任意 `task_kind` 下路由标签都成立。每题默认调用 3 次，用来暴露不稳定：

```powershell
uv run python -m scripts.run_intent_evals --runs 3
```

只调用意图识别，不需要数据库、Milvus 或启动服务；全部通过返回 0。这组题只覆盖单轮、
无历史的问法，多轮指代由离线回归测试覆盖。

## 知识写入冲突检查评测集

`knowledge_consistency_cases.jsonl` 共 20 条候选知识，标签为 `block`（与已有知识重复或冲突，
应拒绝写入）或 `new`（可以写入）：3 条重复、5 条与文档冲突、5 条文档未涉及，另有 7 条是
曾经混入知识库、已清理的人工或挖掘条目。改 `KNOWLEDGE_CONSISTENCY_SYSTEM_TEMPLATE` 后要先跑：

```powershell
uv run python -m scripts.run_consistency_evals --repeats 2
```

每条用本地检索加一次模型调用，需要 MySQL 和 Milvus，不写知识库。除判定外还检查拒绝理由：
须为中文、只引用真实存在的知识编号、不出现“第 1 条”这类位置编号。标签以 `knowledge/`
文档为准，并假设知识库里没有另一条重复候选的人工条目；知识库变化后要重新审核标签，不能改标签迁就结果。
